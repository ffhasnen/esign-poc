Why eSign breaks in the WebView, and how to fix it

eSign currently opens Perfios in a separate Chrome tab instead of staying inside the app, and the result never makes it back. This is a walkthrough of why, and the native-side fix that keeps it in-app — confirmed working end to end.

Findings from a native Android WebView proof of concept · 2026-09-10

01The problem

The host app calls an API to get a CSP URL, loads it in a native Android WebView, and the CSP page (a Flutter web app) has an eSign button that calls window.open() to launch Perfios. That popup pattern assumes a real browser: a genuine popup window with a live window.opener reference back to the page that opened it, so the result can arrive via postMessage.

A native WebView doesn't give you that for free. With no handling wired up, the request either hangs, navigates the same WebView away in place, or — what production actually shows — escapes to the system browser. Once it's in Chrome, there's no relationship back to the app at all; the result can never arrive.

02The fix — native side only

Proven with a working Android proof of concept (Kotlin, two Activities, two WebViews) before writing this up. The shape:

  1. MainActivity starts CspActivity, passing the CSP URL.
  2. CspActivity loads the Flutter app into WebView 1.
  3. Tapping eSign calls window.open() inside WebView 1 — caught by CspActivity's onCreateWindow() instead of escaping to Chrome.
  4. CspActivity starts EsignActivity full screen with the eSign URL, and backgrounds itself.
  5. EsignActivity loads the eSign page into WebView 2. Tapping Success or Fail calls the JS bridge, AndroidEsignBridge.postMessage(json).
  6. EsignActivity validates that JSON, sets it as its Activity result, and finishes — CspActivity resumes and receives it.
  7. CspActivity delivers the result into WebView 1 with evaluateJavascript("window.postMessage(json,'*')") — landing on the Flutter app's own, unchanged messageEventListener.

03What the host app's team needs to build

The host app is React Native, using react-native-webview for the WebView. That library does not reliably support what this fix needs from the JS side: its own native code overwrites any custom WebChromeClient whenever other features are toggled, so the onOpenWindow prop can't be depended on to catch window.open() the way this fix requires.

This has to be native code, not RN props. The fix belongs in the host app's native Android project (the android/ folder every RN app has) — a real native module, written in Kotlin or Java, doing exactly what CspActivity/EsignActivity do in the proof of concept: own the WebChromeClient directly, catch onCreateWindow, launch the eSign screen, and relay the result back. React Native's only job is to call that native module — a single bridge call to kick off the flow, not an attempt to configure it through react-native-webview's props.

04Flutter side

No changes needed for the fix. The PerfiosEsign class's contract — call window.open(), listen for postMessage — is exactly what it was. The native side doing the work above is what makes that contract actually succeed inside a WebView.

Already applied to web/index.html (hygiene, not architecture)

Closed a dangling <script> tag that would have broken the entire eSign block with a syntax error.

window.open() returning null now fails fast as "PopupBlocked" instead of hanging the waiting modal forever.

05Security review

Three issues found and fixed while building the proof of concept, plus one pre-existing gap worth a decision:

  • JS-injection risk, fixed. The eSign page's result now gets parsed and re-serialized as JSON before it can reach another WebView — a raw, unvalidated string pasted into a script would have let a malicious result run arbitrary code in the app.
  • Untrusted content risk, fixed. window.open() is only allowed to open full screen with the native bridge attached for a known-trusted eSign host — not whatever URL happened to be requested.
  • Message spoofing on the JS side, fixed (in the demo). The Flutter page's listener now checks event.origin against an allow-list instead of accepting a result from anywhere. The real app needs Perfios's actual domain here — not guessed, needs to come from the team.
  • Pre-existing, not introduced by this fix. The original listener never checked who sent a message at all — worth confirming whether that's handled elsewhere before shipping.
Why not just let the popup message back directly? In a real browser, the eSign page would call window.opener.postMessage(...) and it would just arrive. WebView 1 and WebView 2 are two separate WebView instances in two separate Activities — there is no opener relationship between them, in any configuration. That's the whole reason the native relay exists.
